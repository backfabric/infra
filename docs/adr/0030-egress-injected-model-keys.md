# Agents reach model providers with a key the egress gateway injects

Amends ADR 0023. Agents reach their model with a provider API key (first an OpenAI API key) that Agent Substrate's egress gateway puts into their requests; the actor holds only a placeholder. Agents no longer log in with a ChatGPT subscription (the device login of agent-0).

The `substrate` subsystem turns on Substrate's egress credential injection with its bundled Kubernetes Secrets provider (`k8s.io`), only while the private repository declares a credential (`backfabric.substrate.credentials.<name>`; none: injection stays off, as before). Each credential comes from a sops secret on the host and is written into a Secret in `agent-credentials`, a namespace that runs no pods (a quota of 0) and admits no traffic, where the provider's service account may `get` exactly the declared Secrets. The provider's upstream ClusterRole, which reads Secrets in every namespace, is removed by the package. The provider's atespace→namespace policy is generated from the declaration: each credential only for the atespaces listed with it (a grant narrowed to the credential's Secret by label). An actor's egress policy names the credential in an `https` rule for the provider's host with `replaceHeaders`; the gateway terminates the actor's TLS with its own CA, asks the provider for the credential with the actor's verified identity, and replaces the placeholder header before the request leaves the cluster. Runbook: docs/substrate.md.

Why:

- A ChatGPT login stores a refresh token in Codex's `auth.json` in the actor's home, so it is in every snapshot of the actor in RustFS; OpenAI: "treat `~/.codex/auth.json` like a password: it contains access tokens" ([Authentication](https://learn.chatgpt.com/docs/auth)). With injection the key is never in the actor, its memory, its environment or its snapshots; Substrate: the actor "cannot read, snapshot, or exfiltrate the secret, nor choose the value that leaves the cluster" ([egress-credential-injection.md](https://github.com/agent-substrate/substrate/blob/v1.0.0/docs/guides/egress-credential-injection.md)).
- A login needs a human per actor (device code), and one login cannot serve many actors: refresh tokens are single-use, and Codex reports `refresh_token_reused` when another copy refreshed first ([codex-rs `login/src/auth/manager.rs`](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/login/src/auth/manager.rs#L224-L229)). OpenAI's CI guide: "Do not share the same file across concurrent jobs or multiple machines" ([ci-cd-auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)). Agents are many actors without a human at each.
- The terms: "You may not share your account credentials or make your account available to anyone else" ([OpenAI Terms of Use](https://openai.com/policies/terms-of-use/)). OpenAI recommends keys for this use: "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs" ([Authentication](https://learn.chatgpt.com/docs/auth)); "The right way to authenticate automation is with an API key" ([ci-cd-auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)).
- Substrate v1.0.0 already does the injection, fail-closed (403 or 503 when the credential cannot be produced), with the provider deciding per actor; we write no gateway or provider.

## Considered Options

- **A ChatGPT subscription login per actor** (the status quo, agent-0): a refresh token in every snapshot, a human login per actor, and all actors on one account's allowance; against "make your account available to anyone else" as soon as several automated agents use it.
- **One subscription held by a credential provider of our own**, refreshing the ChatGPT token and injecting the access token into every actor's requests to `chatgpt.com`: no token in the actors, but it is the pattern OpenAI's guide rules out ("the supported CI/CD strategy is not 'call the refresh API yourself'", [ci-cd-auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)), impersonates Codex's OAuth client with a forged placeholder `auth.json`, and makes one account available to many agents. For Claude subscriptions Anthropic forbids it outright: "developers may not collect, store, or intermediate Claude.ai credentials or session tokens" ([Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)).
- **An LLM gateway in the cluster** (agentgateway, LiteLLM, Envoy): per-actor budgets and model allow-lists in one place, but one more service that sees every prompt, to choose, pin and run. Not needed for one provider and a few agents; it can sit behind the same egress rule later.
- **Workload identity federation** (OpenAI API and Codex, Anthropic API): short-lived tokens exchanged for a signed workload identity, no long-lived provider secret anywhere. The target; later, as its own decision: Substrate cannot yet trade an actor JWT for cloud credentials ([actor-jwts.md](https://github.com/agent-substrate/substrate/blob/v1.0.0/docs/guides/actor-jwts.md#known-limitations)), its provider API has no expiry for a cached token, and Codex's federation is in beta for managed Enterprise workspaces.
- **A credential provider of our own** reading the key from OpenBao (ADR 0009): the key would stay out of etcd, but it is a gRPC service to write and run; the bundled provider with its RBAC narrowed to one namespace is enough now.
- **Upstream's provider as it is**: its ClusterRole reads Secrets in every namespace (upstream calls this a POC scope), and its policy is a ConfigMap edited by hand and read only at startup.

## Consequences

- The gateway intercepts the actors' HTTPS to the provider's host: an actor that uses a credential trusts the gateway's CA (Substrate's projected trust bundle, `egress-mitm.ate.dev`), and the gateway sees those requests in clear text. Whoever controls the gateway in `ate-system` sees prompts and answers, and the key.
- No WebSocket through the gateway (it refuses upgrades with 403): clients must use plain HTTPS (Codex: a custom provider with `supports_websockets = false`).
- The gateway asks the provider for the credential on every request it injects into (no cache in v1.0.0); the provider reads the Secret from the API server each time. A provider outage fails those requests with 503.
- The key is long-lived and sits in etcd (encrypted at rest) and in the private repository's sops file. Rotation: replace the value in sops and deploy; `substrate-credentials` writes the Secret again (sops-nix restarts it when the secret changes), and the next request uses the new key. Revoking it is done at the provider.
- Model use is paid per token on the API key, not on a subscription's allowance.
- Who else can read the Secret: cluster administrators (root on the host) and controllers whose ClusterRoles read Secrets in every namespace (CloudNativePG's operator, ADR 0025). No Substrate component other than the provider.
- Declaring the first credential, or removing the last, makes `substrate-install` run `ate-setup` again (the install document changes); it deploys or removes the provider and restarts the gateway. Removing the last one leaves `agent-credentials` and its Secrets in place (docs/substrate.md has the cleanup).
- The policy is replaced at every deployment that changes it, and the provider's pods restart only then (it loads the policy once at startup).
