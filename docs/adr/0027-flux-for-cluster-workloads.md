# Flux for everything inside the cluster

Everything inside the cluster is delivered by [Flux](https://fluxcd.io/) from the private repository (GitOps); Nix keeps the host, the disks, the network, k3s, and the bootstrap of Flux: the `flux` subsystem (`nix/modules/flux.nix`, runbook docs/flux.md).

- Flux is installed by the [Flux Operator](https://fluxoperator.dev/), the declarative alternative to `flux bootstrap` that Flux's installation guide documents ("Bootstrap with Flux Operator"; `flux install`, the release's `install.yaml` and the community Helm chart are listed there as "Dev install" only). The operator comes from its upstream Helm chart, fetched at build time with a hash and installed by k3s's Helm controller; its image is pinned by digest. One FluxInstance names an exact Flux version, whose controller images the operator pins by digest from the distribution data in its own image; nothing is fetched from the operator's distribution registry, and nothing upgrades without a change here.
- The FluxInstance's sync block makes the operator generate the GitRepository and the Kustomization (prune) for one directory of the private repository, as `flux bootstrap` names them (`flux-system`), without Flux ever writing into the repository.
- The repository is fetched over HTTPS with a read-only GitHub token from the host's sops, rendered into a Kubernetes Secret on the host's tmpfs and applied by k3s; the token is never in the Nix store, an argument, or a log. A GitHub App (`provider: github`) can replace it later without changing the design.
- The synced directory is applied with the controllers' own identity (cluster-admin, Flux's single-tenant default): the private repository already controls the hosts as root, so a narrower identity would not narrow who controls the cluster.
- Upstream charts are installed as they are published, as HelmRelease objects with values, never copied or rewritten. Bootstrap secrets stay in the host's sops; application secrets live in OpenBao (ADR 0009) and reach the cluster through External Secrets Operator, never in Git: Flux decrypts nothing.
- Two repositories, the private one as the root: what every fleet shares (the platform's HelmReleases) is a kustomize base per component under `kubernetes/` of this public repository; the private repository's `clusters/<host>/` pulls it through a second GitRepository pinned to the same commit as its `flake.lock`, and adds host overlays and its own objects (agents). Flux's standard multi-repository layout; host modules and cluster bases come from one version of this repository.

## Considered Options

- Nix-only k3s manifests (the state before this decision): every in-cluster object is a Nix expression written to k3s's manifests directory. Upstream charts have to be rendered or rewritten by hand (Hatchet, #84); k3s keeps what a vanished file created, so removal needs `backfabric.k3s.removedManifests` (#56), which restarts k3s and then races the API server's start (#74); k3s applies files in name order with retries and no notion of readiness or dependencies. Every change to the cluster is also a host deployment.
- Argo CD: the same pull model, but a heavier server with a UI, Redis and its own repository server, and Helm charts rendered by Argo rather than installed as Helm releases; Flux's HelmRelease keeps Helm's own release lifecycle, and its controllers are smaller.
- `flux bootstrap` (CLI or Terraform): Flux's recommended path, but it commits Flux's own manifests into the repository and needs a write-capable credential and an operator machine with cluster access at bootstrap; the install would then live in Git, not in the pinned Nix configuration of the host.
- `flux install --export` built by Nix (closed #44): pinned by nixpkgs' `fluxcd`, but Flux documents it for development only, and any change to the controllers' arguments means patching the generated YAML.
- The fluxcd-community Helm chart through `autoDeployCharts`: maintained on a best-effort basis (Flux's docs), and it does not generate the sync objects.

## Consequences

- Two delivery paths into the cluster: Nix and k3s's manifests for the host-bound parts that exist today (OpenBao's Service, OTel, Substrate, CloudNativePG and the platform PostgreSQL, the admission policies) and for Flux's bootstrap; Flux for everything new. An object has exactly one of them as owner. Moving the existing modules to Flux is later work, one PR each; the hardening (Pod Security, admission policies, the API server's flags) stays in Nix.
- Prune, `dependsOn`, `wait` and health checks replace `removedManifests` and the ordering races for what Flux delivers; a change to the cluster is a push to the private repository, applied by the cluster itself within a minute, without the operator's machine or a host deployment.
- Whoever can push to the synced branch controls the cluster; branch protection on the private repository is the control.
- The cluster pulls the operator's and Flux's images from `ghcr.io` (by digest), and needs GitHub to apply changes; what runs keeps running without either.
- The token is the operator's to create, store in sops, and renew before it expires; an expired token stops delivery, not workloads. Replacing it restarts k3s (pods keep running).
- Upgrading Flux or the operator is a change of version, hash and digest in `nix/modules/flux.nix` and a deployment.
- Shared cluster content in `kubernetes/` changes with this repository's commits; a fleet takes it, together with the modules, by moving its pin. Keeping the GitRepository's commit equal to `flake.lock` is the operator's step (documented), not enforced by code.
