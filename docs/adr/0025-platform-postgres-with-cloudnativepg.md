# Platform PostgreSQL with CloudNativePG

Platform services that need a relational store (first the A2A front door's task store and Hatchet) share one PostgreSQL in the cluster, run by the [CloudNativePG](https://cloudnative-pg.io/) operator: the `postgres` subsystem (`nix/modules/postgres.nix`, runbook docs/postgres.md).

- The operator comes from CloudNativePG's release manifest (`cnpg-<version>.yaml`), fetched with a hash and patched at build time so that every image reference carries a digest; the build fails if one does not. k3s deploys it like any other manifest. Upstream asks for `kubectl apply --server-side` because the CRDs do not fit kubectl's client-side `last-applied-configuration` annotation (256 KiB); k3s's deploy controller (wrangler's apply) keeps a gzipped copy with strings cut to 64 bytes instead (about 28 KB for the largest CRD), so no separate apply step is needed.
- One Cluster, `platform` in the namespace `postgres`, with one instance: PostgreSQL from CloudNativePG's minimal image, pinned by digest, on a static `local` PersistentVolume in `/var/lib/postgres-platform` (the encrypted btrfs file system, ADR 0003), bound to the instance's claim by name, with a storage class that no provisioner serves and no StorageClass object, as Substrate's volumes (ADR 0023). Reclaim policy Retain: the data outlives the claim, the volume, and the subsystem.
- CloudNativePG's defaults otherwise: TLS with its own CA, which it renews; every pod passes Pod Security `restricted` (non-root uid 26, no capabilities, RuntimeDefault seccomp, read-only root file system), so no exemption from ADR 0017 is needed. The `postgres` superuser cannot log in over the network (`enableSuperuserAccess: false`).
- Databases are declared in the host configuration: each a CloudNativePG `Database` owned by a role managed in the Cluster's `managed.roles` (not the `DatabaseRole` CRD that 1.30 introduces: inline roles are reconciled against the database as well, and carry no finalizer that could hold the namespace when the subsystem is turned off). pg_hba admits each owner only to its own database, only over TLS, and rejects every other network login. The role's password is random, generated on the host into a Secret in `postgres` (never stored in the repository or sops), and copied with the connection details and the CA into a Secret in the service's namespace, at every deployment and daily (the CA is renewed every 83 days).
- NetworkPolicy denies all ingress to `postgres` except from the operator and, to port 5432, from the namespaces of the declared databases; in `cnpg-system` only the operator's webhook is reachable.

## Considered Options

- Substrate's bundled PostgreSQL (ADR 0023): it belongs to Substrate, authenticates only pods with Substrate's pod certificates, and is installed and upgraded by `ate-setup`; sharing it would tie the platform services' data to Substrate's lifecycle.
- A static StatefulSet with the upstream `postgres` image: no operator, but we would write and own initialisation, role and database creation, TLS, password rotation, upgrades, and later backups and replicas; the official image's entrypoint starts as root, so it would also not pass `restricted` without changes.
- PostgreSQL on the host as a NixOS service (as OpenBao, ADR 0009): reachable from every pod through `cni0`, since the host firewall cannot tell pods apart; access per namespace needs NetworkPolicy, which only works in the cluster. Unlike OpenBao, it does not need to work while the cluster is down: its clients are pods.
- Other operators (Zalando's postgres-operator, Crunchy PGO, StackGres): heavier (Patroni, more images and components), and less aligned with plain Kubernetes primitives; CloudNativePG is a CNCF project with declarative databases and roles, and a backup plugin for S3.
- Passwords in sops (generated by `backfabric keygen`): keygen has a fixed list of secrets, and the databases are the consumer's; every new database would need a code change or a manual sops step. The passwords are only needed inside the cluster.

## Consequences

- One instance: no failover. A node or volume failure stops every platform service that uses it; the data is on the host's RAID1 (ADR 0003), but nothing else protects it.
- No backups yet. The next step is CloudNativePG's Barman Cloud plugin writing to an S3 store (RustFS), which needs cert-manager; until then losing the host or the directory loses the data.
- `/var/lib/postgres-platform` holds every platform service's data; its size is fixed once the claim exists (no resize: static volume) and not enforced (it shares the host's file system).
- k3s restarts when the subsystem is enabled or disabled (its `--disable` list changes). Turned off, k3s deletes what the manifests applied, including the CRDs and the `postgres` namespace. The files stay on the host, but turning it on again does not reuse them: CloudNativePG bootstraps a new, empty cluster and renames the old data directory to `pgdata_<timestamp>`; it has no supported way to adopt an existing data directory. Before turning it off, every database is dumped, and restored afterwards (docs/postgres.md).
- Upgrades of the operator and PostgreSQL are a version, a hash, and digests in `nix/packages/cloudnative-pg.nix`; a PostgreSQL major upgrade follows CloudNativePG's procedure.
