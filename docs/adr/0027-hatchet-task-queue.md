# Hatchet as the platform's task queue

The dispatcher, the platform's A2A front door, queues agent turns: one turn at a time per conversation (A2A `contextId`), a global cap on concurrent turns, retries and timeouts, and a view of what runs. The queue is [Hatchet](https://hatchet.run/) (MIT), run in the cluster by the `hatchet` subsystem (`nix/modules/hatchet.nix`, runbook docs/hatchet.md), from its release images (v0.114.2), pinned by digest.

- **PostgreSQL only.** Hatchet keeps its state and, with `SERVER_MSGQUEUE_KIND=postgres`, its message queue in one PostgreSQL database: `hatchet` on the platform PostgreSQL (ADR 0025), declared through `backfabric.postgres.databases`. No RabbitMQ (Hatchet's default): one fewer stateful service to run, secure and back up, for a load of agent turns that each take minutes.
- **What it stores: ids only.** The dispatcher's own database holds the canonical record of every A2A message, task, status and artifact; an agent's working state lives in its Substrate actor. A Hatchet run's input and output carry only ids (task, context, agent), so Hatchet's tables can be lost and rebuilt from the dispatcher's record, and its dashboard shows no conversation content.
- **Hand-written objects, not the Helm chart.** The objects (three Deployments, their Services, NetworkPolicies, RBAC for the setup Jobs) are written in Nix and rendered into one k3s manifest whose build fails on an image reference without a digest, as CloudNativePG's (ADR 0025). The official chart (`hatchet-stack`) would need its Bitnami subcharts fetched even when disabled, names its setup Job with `randAlphaNum` (a different manifest at every render), runs migrations from Helm hooks that k3s does not run, uses an unpinned `alpine` placeholder, and sets no security context by default (the optional one sets only the user); patching all of that would be longer than the objects themselves.
- **Pod Security `restricted`** for every pod (non-root uid 65532, no capabilities, RuntimeDefault seccomp, read-only root file system): Hatchet's images are static Go binaries and a static file server that need nothing more. No exemption from ADR 0017.
- **gRPC without TLS inside the cluster.** Workers and clients reach the engine at `hatchet-engine.hatchet.svc:7070` in plaintext. Hatchet's TLS would need a CA and certificates we issue, rotate and distribute to every client, for traffic that never leaves the node; NetworkPolicy instead admits only the namespaces in `backfabric.hatchet.clientNamespaces`, and every call carries a tenant token. The token and the payloads (ids only) cross the pod network unencrypted; when the cluster has more than one node, this decision is revisited (flannel's WireGuard backend or TLS on the engine).
- **No ingress.** The namespace denies all ingress and egress except DNS, PostgreSQL, the engine's gRPC from the API and the client namespaces, the API from the dashboard, and the Kubernetes API from the setup Jobs. The dashboard is reached with `kubectl port-forward` only (it proxies `/api` to the API), as everything else in the cluster (ADR 0017). Hatchet's startup security check (a request to `security.hatchet.run`) is off.
- **Secrets generated in the cluster, never committed.** A host oneshot, `hatchet-credentials` (as `postgres-credentials`), at every deployment and boot: generates the dashboard admin's password into a Secret; runs Hatchet's own `hatchet-admin k8s quickstart` once in a Job to generate the encryption keysets and cookie secrets into the Secret `hatchet-keys`; and, once per client namespace, `hatchet-admin k8s create-worker-token` in a Job (a token of the default tenant), copied into the Secret `hatchet-client-token` of that namespace with the SDK's variables. The Jobs' service account may only create Secrets in `hatchet` and read or update the ones it writes. Sign-up, invites and new tenants are off; the API seeds the admin and the default tenant at startup. Keys in sops (`backfabric keygen`) were the alternative: keygen would need Hatchet's Tink keyset format, and these secrets are only ever used inside the cluster.
- **Startup.** The engine and the API run `hatchet-migrate` as an init container (goose under a PostgreSQL session lock, so both may run at once, and every upgrade migrates before the new version starts); it retries its first connection for 30 seconds, which covers the delay before kube-router admits a new pod's address (ADR 0025).

## Considered Options

- [Temporal](https://temporal.io/): the reference for durable execution, but a cluster of services (frontend, history, matching, worker) plus Elasticsearch or a SQL visibility store, and per-key concurrency only through workflow design; much more to run for one queue.
- River or another PostgreSQL job library inside the dispatcher: no separate service, but the dispatcher would own scheduling, concurrency per key, retries, timeouts and a dashboard; Hatchet has concurrency groups by key (`GROUP_ROUND_ROBIN`/`CANCEL_NEWEST`), a global cap through worker slots, and a dashboard.
- Hatchet with RabbitMQ: Hatchet's default for high throughput; a second stateful service with its own credentials and storage for load we do not have.
- Hatchet Cloud: the queue, its tokens and its dashboard outside our cluster and audit.
- `hatchet-lite` (engine, API and dashboard in one image): one Deployment, but upstream positions it for development, and it cannot be scaled or upgraded per component.
- TLS on the engine with a CA from cert-manager or OpenBao: deferred until traffic leaves the node (above).

## Consequences

- Hatchet's data shares the platform PostgreSQL's volume and its lack of backups (ADR 0025); losing it loses queued and running turns, which the dispatcher can resubmit from its record.
- The encryption keys and the admin password live only in the namespace `hatchet`. Turning the subsystem off deletes the namespace and them; the database stays and holds data encrypted with the old keys and the old admin, so before enabling it again the database is dropped (docs/hatchet.md). Client namespaces keep a stale `hatchet-client-token` until `hatchet-credentials` replaces it.
- Tokens are minted once per client namespace with a 100-year expiry; rotating one is deleting its Secret in `hatchet` (docs/hatchet.md). A namespace removed from `clientNamespaces` loses its Secrets (`hatchet-credentials` deletes the ones it labelled) and its network access, but its token stays valid: replaced or removed tokens must be revoked in the dashboard, since `hatchet-admin` cannot revoke them.
- The dashboard's session cookie is set for `http://localhost:8080` (the port-forward); reaching the dashboard any other way needs `SERVER_URL` and the cookie settings changed, and a decision on ingress.
- Upgrading Hatchet is a version and five digests in `nix/modules/hatchet.nix`; migrations run before the new pods start. Hatchet releases often; upgrades follow its release notes for breaking migrations.
