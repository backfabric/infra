# Flux delivers the agents; Nix delivers the platform

Two delivery paths into the cluster, split by trust. Nix delivers the host, k3s, and the whole platform (kagent and the Substrate fork it installs, agentgateway, CloudNativePG, OpenBao, External Secrets Operator), upstream Helm charts as they are published through nixpkgs' `services.k3s.autoDeployCharts` (fetched with a hash, values in Nix) and k3s's manifests; kagent and its Substrate fork instead through kagent's own installer, run by Nix (ADR 0030). [Flux](https://fluxcd.io/) delivers only the agents, from a directory of the private repository, with no more rights than the agents' kinds in the agents' namespace: the `flux` subsystem (`nix/modules/flux.nix`, runbook docs/flux.md).

- Flux is installed by the [Flux Operator](https://fluxoperator.dev/), the declarative alternative to `flux bootstrap` that Flux's installation guide documents ("Bootstrap with Flux Operator"; `flux install`, the release's `install.yaml` and the community Helm chart are listed there as "Dev install" only). The operator comes from its upstream Helm chart through `autoDeployCharts`, its image pinned by digest, its unauthenticated web UI off. One FluxInstance names an exact Flux version, whose controller images the operator pins by digest from the distribution data in its own image; nothing upgrades without a change here.
- Flux runs with the operator's multi-tenancy lockdown: no Flux object ever acts with the controllers' cluster-admin identity (a missing service account means the namespace's `default`, with no rights), no cross-namespace references, no remote kustomize bases.
- Nix creates the agents' namespace, a service account in `flux-system`, and a Role in the agents' namespace that allows only listed kinds (an option; ConfigMaps for now, kagent's kinds later). The GitRepository and the Kustomization are Nix's too, in `flux-system`; the Kustomization applies the directory impersonating that service account. A commit that asks for anything else (another namespace, cluster-scoped kinds, RBAC, Secrets, ServiceAccounts, Flux's kinds) is refused by the API server; the module refuses such kinds in the option at evaluation. The operator's own `sync` is not used, because in multi-tenant mode its Kustomization runs as kustomize-controller.
- The repository is fetched over HTTPS with a read-only GitHub token from the host's sops, rendered into a Secret in `flux-system` on the host's tmpfs and applied by k3s: never in the Nix store, an argument, a log, or the agents' namespace. Application secrets live in OpenBao (ADR 0009) and reach the cluster through External Secrets Operator, never in Git: Flux decrypts nothing.

## Considered Options

- Flux for everything inside the cluster, with a cluster-admin sync and the platform as HelmReleases (this PR's first design): `dependsOn`, health checks and prune for the platform, but then a push to the synced directory is cluster-admin, and the agents' directory, written by agents and their users, is the least trusted input there is. Splitting the repository by trust within Flux (a root sync for the platform plus a tenant for agents) keeps two delivery paths anyway, and the platform's versions would no longer move with the host's `flake.lock`.
- Nix only, agents as k3s manifests: every agent change is a host deployment, and k3s applies with cluster-admin; no pull model, no prune of an agent removed from the directory without `removedManifests`.
- Argo CD for the agents: an AppProject restricts kinds and namespaces as well, but it is a heavier server (UI, Redis, repository server) for one directory of plain manifests.
- `flux bootstrap`, `flux install --export` (closed #44), the community chart: see above; #44's impersonation and RBAC allowlist are reused here, its ValidatingAdmissionPolicy is not needed because a Role in one namespace is the boundary.

## Consequences

- The platform keeps the costs of k3s manifests and `autoDeployCharts`: no `dependsOn`, readiness or health between charts, ordering by retries; removal needs `backfabric.k3s.removedManifests` (#56), which restarts k3s and races the API server's start (#74). In exchange the platform's versions are pinned with the host in `flake.lock` and change only with a deployment.
- Agents are pulled: a push to the agents' directory reaches the cluster within a minute without a deployment or the operator's machine; an agent removed from the directory is deleted (prune). A push can do no more than the listed kinds in the agents' namespace; each new kind is a change of `allowedResources` in Nix.
- The agents' namespace belongs to Nix; turning Flux off deletes it with everything in it.
- The cluster pulls the operator's and Flux's images from `ghcr.io` (by digest), and needs GitHub to apply changes to the agents; what runs keeps running without either.
- The token is the operator's to create, store in sops, and renew before it expires; an expired token stops delivery, not workloads. Replacing it restarts k3s (pods keep running).
- Upgrading Flux or the operator is a change of version, hash and digest in `nix/modules/flux.nix` and a deployment.
