# Every namespace is declared in Nix and closed by default

Amends ADR 0017, which left the per-namespace NetworkPolicies to the workloads. A namespace without a NetworkPolicy is open: all ingress and egress of its pods is allowed. Namespaces appeared wherever something created them (module manifests, installers, a oneshot, `kubectl` by hand), and some had no policies at all.

So the `k3s` subsystem makes the set of namespaces part of the configuration:

- `backfabric.k3s.namespaces.<name>` declares every namespace. `createdBy` is `"nix"` by default: the Namespace object is generated into the k3s manifest `backfabric-namespaces`. Any other value names an external creator (k3s, ate-setup, another manifest, a person) and needs a `reason`; such a namespace is only admitted.
- `networkPolicies` is `"default-deny"` by default: the same manifest gets, per namespace, `backfabric-default-deny` (every pod, ingress and egress), `backfabric-allow-dns` (egress to CoreDNS in kube-system, UDP and TCP 53), and `backfabric-allow` with the declared `ingress` and `egress` rules, raw NetworkPolicy rules applied to every pod. Modules may add their own NetworkPolicies for single pods. `"unmanaged"` generates none and needs a `reason`.
- The ValidatingAdmissionPolicy `backfabric-declared-namespaces` (in the same manifest, `failurePolicy: Fail`, binding `Deny` and `Audit`) rejects the CREATE of a Namespace whose name is not declared, with a message naming the option. Only CREATE: a namespace's name cannot change, so an update cannot bring an undeclared namespace into existence, and rejecting updates would wedge namespaces that existed before their declaration (installers re-apply them, controllers label them). Label changes are not checked by this policy.
- k3s's namespaces are declared by the k3s module: `kube-system` is unmanaged (CoreDNS answers every pod, and the Helm controller's jobs run there; closing it would need rules for each k3s component, kept in step with k3s releases); `default`, `kube-public` and `kube-node-lease` are closed (no pods run there; the API server's `kubernetes` Service in `default` is not a pod and stays reachable).
- Removing a declaration removes what was generated for it: `backfabric-namespaces` is always deployed, and k3s prunes the objects that disappear from it. A namespace Nix created is deleted with everything in it; one created elsewhere stays, without the generated policies, and cannot be created again while undeclared. One manifest instead of one per namespace: a per-namespace file left behind would need its name in `removedManifests` by hand, or its symlink would dangle after garbage collection and stop k3s's manifest processing.

The modules declare their namespaces as they are created today, as exceptions with their reasons (postgres, cnpg-system, otel, openbao, ate-system, podcertificate-controller-system, the namespaces of `backfabric.postgres.databases`, of `backfabric.substrate.workerPoolNamespaces`, and the smoke test's). Moving each to the generated Namespace and default-deny is one change per module, checked on a node: moving a Namespace object between two k3s manifests must not let the old manifest prune it.

## Considered Options

- Cluster-wide policies: [AdminNetworkPolicy and BaselineAdminNetworkPolicy](https://network-policy-api.sigs.k8s.io/reference/spec/) (`policy.networking.k8s.io/v1alpha1`) would close every namespace with one object. k3s 1.36's embedded NetworkPolicy controller ([kube-router](https://github.com/k3s-io/kube-router)) implements only `networking.k8s.io/v1` NetworkPolicy, and the API is being reworked as [ClusterNetworkPolicy](https://network-policy-api.sigs.k8s.io/blog/2025/10/09/api-update-for-v1alpha2-clusternetworkpolicy-replaces-adminnetworkpolicy-and-baselineadminnetworkpolicy/) (`v1alpha2`, alpha). Using it would mean replacing the embedded controller with another one.
- kube-router's `--netpol-default-deny` ([cloudnativelabs/kube-router#2079](https://github.com/cloudnativelabs/kube-router/pull/2079); not exposed by k3s yet, [k3s-io/k3s#14711](https://github.com/k3s-io/k3s/issues/14711)): rejects traffic of pods whose policy chains are not programmed yet, closing the startup race for pods a policy selects. It does not close a namespace without policies. Worth adding once k3s exposes it, as defence in depth.
- A controller that generates the policies for every namespace (Kyverno `generate`, or our own): reacts to namespaces created anywhere, but is one more privileged component with its own deployment, webhook and failure modes; the declared set is already known at evaluation time.
- nftables on the host (on `cni0`): cannot tell namespaces or pods apart without reimplementing kube-router's ipsets, and hand-written rules for pod traffic are what ADR 0017 and ADR 0018 avoid.
- A label set only by Nix that a policy requires on new namespaces: anyone allowed to create namespaces can set the label too; the name list in the policy is the declaration itself.
- Starting the policy in `Warn`: nothing that creates namespaces today is undeclared after this change, and an existing namespace is never blocked.

## Consequences

- Every module declares the namespaces it uses; a host configuration declares those of its workloads. A namespace created by any other path is rejected, visibly (the client's error, the audit log).
- Externally created namespaces and unmanaged policies are explicit exceptions, each with a reason, readable in `config.backfabric.k3s.namespaces`.
- A pod in a closed namespace reaches nothing but DNS until rules are declared. Services on the host (the API server on 6443, OpenBao, the Collector) are reached at the node's address after kube-proxy's translation, so they need an egress rule with an `ipBlock` of that address.
- Removing a declaration of a namespace Nix created deletes it and everything in it, as removing a manifest with a Namespace does (ADR 0017's removed manifests); changing its `createdBy` away from `"nix"` does the same.
- A cluster admin can still delete the policy or its binding; until k3s applies the manifest again (it does when the file changes, and at k3s's start), namespaces can be created freely. The same holds for `backfabric-deny-external-services` (ADR 0017). Namespaces created before the policy existed are not affected by it.
- Agents do not get a namespace each: actors are isolated by Substrate's sandboxes, identities and per-actor egress (ADR 0023), inside the WorkerPool namespaces the host declares.
- Policies for a namespace an external creator has not created yet fail to apply until it exists; k3s retries the manifest every 15 seconds, and wrangler applies the rest of it meanwhile.
