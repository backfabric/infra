# Flux

The `flux` subsystem makes the private repository the source of everything
inside the cluster ([ADR 0027](adr/0027-flux-for-cluster-workloads.md)).
Nix installs the [Flux Operator](https://fluxoperator.dev/) and one
FluxInstance; Flux then applies one directory of the repository (e.g.
`clusters/node1/`) and keeps the cluster equal to it. The host, disks,
network, k3s and this bootstrap stay in Nix. It is off by default:

```nix
backfabric.flux = {
  enable = true;
  repository = {
    url = "https://github.com/<owner>/<repository>";
    path = "./clusters/node1";
    branch = "main";             # the default
    tokenSecret = "flux-git-token"; # the default, in secrets/common.yaml
  };
};
```

| What | Where |
| ---- | ----- |
| Flux Operator | Helm release `flux-operator` in `flux-system`, from the upstream chart `oci://ghcr.io/controlplaneio-fluxcd/charts/flux-operator` 0.62.1 (k3s HelmChart `kube-system/flux-operator`, manifest `flux-operator`) |
| Flux | FluxInstance `flux-system/flux` (manifest `flux-instance`): Flux 2.10.0, source-, kustomize-, helm- and notification-controller, images by digest |
| Sync | GitRepository and Kustomization `flux-system/flux-system`, generated by the operator: `ref` `refs/heads/<branch>`, fetched every 1m; the Kustomization applies `path` with prune every 10m and on every new revision |
| Git credential | Secret `flux-system/flux-system` (`username: git`, `password`: the token), rendered by sops-nix into `/run/secrets/rendered/flux-git-credentials.yaml` (root, 0400), deployed by k3s (manifest `flux-git-credentials`) |

## What runs, and what is ours

Everything in the cluster is upstream: the operator's chart as published
(only `image.tag` is set, to the same version pinned by digest), and the
Flux distribution the operator renders from the data in its image,
including Flux's NetworkPolicies (`allow-egress`, `allow-scraping`,
`allow-webhooks`) and its namespace labels (Pod Security `warn:
restricted`; the cluster's default enforces `restricted`, which every
Flux and operator pod passes, so `flux-system` needs no exemption).

Ours is `nix/modules/flux.nix`: the FluxInstance (version, registry, and
the sync block), and the Secret rendered from sops. The chart and its
hash, the operator image digest, and the Flux version are pinned there;
an upgrade is a change of those values and a deployment.

The Kustomization applies with the controllers' own identity
(cluster-admin, Flux's single-tenant default): whoever can push to the
synced branch controls the cluster, as they already control the hosts
through the same repository.

## The token

A fine-grained personal access token, read-only, for the private
repository only: GitHub, Settings, Developer settings, Personal access
tokens, Fine-grained tokens, Generate new token:

- Resource owner: the owner of the repository; Repository access: Only
  select repositories, the private repository;
- Repository permissions: Contents: Read-only (Metadata: Read-only is
  added); nothing else;
- an expiry you note somewhere: when it expires, Flux stops fetching (the
  GitRepository turns not Ready); what runs stays.

Add it to the cluster-wide sops file (`backfabric keygen` does not
generate it): `sops secrets/common.yaml`, add the line
`flux-git-token: github_pat_...`, save. Check, without printing it:

```sh
sops -d --extract '["flux-git-token"]' secrets/common.yaml | cut -c1-11   # github_pat_
```

The value never enters the Nix store, an argument, or a log: sops-nix
renders the Secret into `/run/secrets/rendered` (a tmpfs) and k3s applies
the file. k3s keeps a copy of every object it applies, with strings cut to
64 characters, in the object's own annotation
`objectset.rio.cattle.io/applied`, so the Secret carries a prefix of the
token in itself: readable by exactly those who can read the Secret, and
encrypted at rest like it.

Replacing the token: change it in `secrets/common.yaml`, commit, deploy.
The deployment restarts k3s (pods keep running): k3s only re-reads a
manifest whose link changed, and the link to the rendered file does not.

Application secrets do not go into the repository: they live in OpenBao
(ADR 0009) and reach the cluster through External Secrets Operator. Flux
has no decryption configured.

## The repository

`path` is a kustomization (or plain manifests) of the private repository,
e.g. `clusters/node1/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources: []
```

Every object Flux applies from it carries the labels
`kustomize.toolkit.fluxcd.io/name: flux-system` and
`kustomize.toolkit.fluxcd.io/namespace: flux-system`. An object removed
from the directory is deleted from the cluster (prune). Upstream Helm
charts are installed as HelmRepository or OCIRepository plus HelmRelease
objects, with values, not copies of the chart. Order between parts is
expressed with further Flux Kustomizations and `dependsOn` / `wait`.

Nothing Flux applies may conflict with the manifests Nix deploys through
k3s (`kubectl -n kube-system get addon`): one owner per object.

## Bases from backfabric/infra

Cluster content that every fleet shares (the platform's HelmReleases)
lives in this public repository, under
[`kubernetes/`](../kubernetes/README.md), one kustomize base per component:
`kubernetes/<component>/`. The private repository stays the root source:
its `clusters/<host>/` declares a second GitRepository for
backfabric/infra, pinned to a commit, and one Flux Kustomization per base
it wants, with host-specific overlays; its own objects (agents, host
values) sit next to them. Flux's standard multi-repository layout; the
bootstrap needs nothing for it, since the synced Kustomization may create
Flux objects.

`clusters/node1/backfabric.yaml`, listed in its `kustomization.yaml`:

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: backfabric
  namespace: flux-system
spec:
  url: https://github.com/backfabric/infra   # public: no secretRef
  ref:
    commit: <the backfabric rev in flake.lock>
  interval: 1h
  ignore: |
    /*
    !/kubernetes/
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: <component>
  namespace: flux-system
spec:
  sourceRef:
    kind: GitRepository
    name: backfabric
  path: ./kubernetes/<component>
  interval: 10m
  prune: true
  wait: true
  # dependsOn: [{ name: <another component> }]
  # Host overlays: kustomize patches on the base's objects, e.g. a
  # HelmRelease's values.
  # patches:
  #   - target: { kind: HelmRelease, name: <component> }
  #     patch: |
  #       - op: add
  #         path: /spec/values/replicaCount
  #         value: 1
```

Pin the same commit as the `backfabric` input in `flake.lock`, so that
the host's modules and the cluster's bases come from one version of this
repository, and change both in one commit:

```sh
nix flake update backfabric
nix eval --raw --impure --expr '(builtins.fromJSON (builtins.readFile ./flake.lock)).nodes.backfabric.locked.rev'
# set ref.commit in clusters/<host>/backfabric.yaml to it, commit, push
```

## Status

On the host, as root:

```sh
kubectl -n flux-system get fluxinstance,pods
kubectl -n flux-system get gitrepository,kustomization,helmrelease
kubectl -n flux-system describe kustomization flux-system   # conditions, inventory
kubectl -n flux-system logs deploy/kustomize-controller
kubectl -n kube-system get helmchart flux-operator
```

`fluxinstance/flux` is `READY True` with `Reconciliation finished`;
`gitrepository/flux-system` shows the fetched revision
(`main@sha1:<commit>`), `kustomization/flux-system` the applied one.

Fetch and apply now instead of waiting for the interval:

```sh
kubectl -n flux-system annotate --overwrite gitrepository/flux-system reconcile.fluxcd.io/requestedAt="$(date +%s)"
kubectl -n flux-system annotate --overwrite kustomization/flux-system reconcile.fluxcd.io/requestedAt="$(date +%s)"
```

The `flux` CLI (`nix shell nixpkgs#fluxcd`, may be a version behind)
shows the same with `flux get all -A`, and does the above with `flux
reconcile kustomization flux-system --with-source`.

## Failures

- `gitrepository/flux-system` not Ready with an authentication error: the
  token expired, was revoked, or lacks access to the repository. Replace
  it (above). Until then nothing new is applied; what runs stays.
- `kustomization/flux-system` not Ready: the message names the object and
  the error (a build error of the kustomization, a rejection by the API
  server: Pod Security, the NodePort/LoadBalancer policy). The previous
  revision stays applied.
- `fluxinstance/flux` missing or `helmchart/flux-operator` failing: the
  chart release failed; `kubectl -n kube-system logs job/helm-install-flux-operator`.
- No pods in `flux-system`: images come from `ghcr.io`; the cluster needs
  registry access.

## Turn off

Turned off, the next deployment removes the three k3s manifests: k3s
deletes the Secret and the FluxInstance, and uninstalls the operator's
release (its CRDs stay). Delete the FluxInstance first, while the operator
still runs, so that it removes the Flux controllers; what Flux applied
stays in the cluster:

```sh
ssh node1 kubectl -n flux-system delete fluxinstance flux --wait
# then set backfabric.flux.enable = false, commit, deploy
backfabric deploy node1
```

The deployment restarts k3s (its `--disable` list changes).
